# ГЭ 1. Объектно-ориентированное программирование: подробный ответ

Расширенная версия ответа. Основа: ранее указанные источники по ООП, паттернам проектирования, C/C++ и стандартные учебные формулировки объектно-ориентированного анализа и проектирования.

---

## 1. Качество ПО. Внешние и внутренние факторы

### 1.1. Что такое качество ПО

Качество программного обеспечения - это не только отсутствие ошибок. Более строго, качество означает способность программы удовлетворять явно заданные требования и разумно ожидаемые потребности пользователей, заказчиков и разработчиков.

Важно различать:

- качество результата работы программы;
- качество самой программы как инженерного изделия;
- качество процесса разработки.

Например, программа может выдавать правильный результат сегодня, но быть плохо написанной. Тогда внешне она пока выглядит приемлемой, но внутреннее качество низкое, и при изменении требований начнутся ошибки.

### 1.2. Внешние факторы

Внешние факторы видны пользователю и заказчику.

| Фактор | Уточнение |
|---|---|
| Корректность | программа делает то, что указано в спецификации |
| Надежность | программа сохраняет работоспособность при нормальных и допустимых нештатных ситуациях |
| Удобство использования | интерфейс и сценарии работы понятны пользователю |
| Эффективность | приемлемые время работы и расход памяти |
| Безопасность | защита данных, прав доступа и операций |
| Совместимость | работа с нужной ОС, БД, форматами, библиотеками |
| Функциональная полнота | реализованы требуемые возможности |

Корректность относится к соответствию спецификации. Надежность шире: программа может быть корректной на правильных данных, но ненадежной при ошибках ввода или сбоях окружения.

### 1.3. Внутренние факторы

Внутренние факторы видит разработчик.

| Фактор | Уточнение |
|---|---|
| Читаемость | код можно понять без чрезмерных усилий |
| Модульность | система разбита на части с ясной ответственностью |
| Сопровождаемость | ошибки и изменения можно вносить локально |
| Расширяемость | новые функции добавляются без разрушения старого кода |
| Тестируемость | код можно проверять автоматическими тестами |
| Повторное использование | компоненты пригодны в разных контекстах |
| Низкое сцепление | модули мало зависят друг от друга |
| Высокая связность | элементы одного модуля относятся к одной задаче |

Внутреннее качество является основой внешнего качества. Если классы перемешивают разные обязанности, имеют глобальные зависимости и скрытые побочные эффекты, то надежность и корректность быстро ухудшаются.

### 1.4. Как отвечать на экзамене

Сначала дать определение качества, затем разделить факторы на внешние и внутренние, после этого объяснить связь: пользователь видит внешнее качество, но разработчик обеспечивает его через внутреннюю структуру программы.

Типичная ошибка: перечислить только удобство и скорость, забыв про сопровождаемость, тестируемость и модульность.

## 2. Модульность. Критерии, правила, принципы

### 2.1. Понятие модуля

Модуль - самостоятельная часть программной системы, которая имеет назначение, интерфейс и реализацию.

В ООП модулем может быть:

- класс;
- интерфейс;
- пакет;
- библиотека;
- компонент;
- подсистема.

Интерфейс показывает, что модуль предоставляет. Реализация показывает, как он это делает. Хороший модуль скрывает реализацию и раскрывает только необходимые операции.

### 2.2. Критерии модульности

Классические критерии:

| Критерий | Смысл |
|---|---|
| Декомпозируемость | сложную задачу можно разбить на подзадачи |
| Компонуемость | готовые модули можно собирать в новые системы |
| Понятность | модуль можно изучать отдельно |
| Непрерывность | малое изменение требований вызывает малое изменение кода |
| Защищенность | ошибка локализуется внутри модуля |

Непрерывность особенно важна: если изменение названия поля в одном классе требует исправить десятки файлов, модульность плохая.

### 2.3. Связность и сцепление

Связность внутри модуля должна быть высокой. Это значит, что все элементы модуля работают ради одной ответственности.

Сцепление между модулями должно быть низким. Это значит, что модуль зависит от минимального числа других модулей и желательно от их интерфейсов, а не реализаций.

Плохой пример:

```text
Класс Order одновременно хранит заказ, печатает чек, отправляет email и работает с базой данных.
```

Хороший вариант:

```text
Order хранит состояние заказа.
OrderRepository отвечает за сохранение.
ReceiptPrinter отвечает за печать.
NotificationService отвечает за уведомления.
```

### 2.4. Правила модульности

Правила:

1. Делать интерфейсы малыми.
2. Делать зависимости явными.
3. Не раскрывать внутренние данные.
4. Разделять разные ответственности.
5. Избегать глобального состояния.
6. Не связывать модуль с конкретной реализацией без необходимости.

### 2.5. Принципы SOLID

SOLID - набор принципов объектно-ориентированного проектирования.

| Принцип | Смысл |
|---|---|
| Single Responsibility | у класса одна причина для изменения |
| Open/Closed | класс открыт для расширения, но закрыт для изменения |
| Liskov Substitution | наследник должен заменять базовый класс без нарушения корректности |
| Interface Segregation | лучше несколько малых интерфейсов, чем один большой |
| Dependency Inversion | зависеть от абстракций, а не от конкретных классов |

На экзамене не обязательно углубляться в SOLID, но полезно связать его с модульностью.

## 3. Повторное использование. Повторяемость. Требования к модульным структурам

### 3.1. Повторное использование

Повторное использование - применение уже созданного кода или проектного решения в другом месте.

Уровни повторного использования:

- готовые функции;
- классы;
- обобщенные типы;
- библиотеки;
- компоненты;
- фреймворки;
- паттерны проектирования;
- архитектурные решения.

### 3.2. Наследование и композиция

Наследование повторно использует код через отношение "является".

Композиция повторно использует код через отношение "содержит".

Композиция часто безопаснее, потому что не создает жесткой иерархии. Наследование нужно применять, когда наследник действительно является частным случаем базового типа.

### 3.3. Повторяемость

Повторяемость - способность модуля или решения многократно применяться без копирования и без нарушения корректности.

Условия повторяемости:

- ясный контракт;
- независимость от конкретного окружения;
- отсутствие скрытых побочных эффектов;
- параметризация;
- тестируемость;
- документированность;
- стабильный интерфейс.

### 3.4. Требования к модульным структурам

Модульная структура должна быть:

- простой для понимания;
- устойчивой к изменениям;
- пригодной к тестированию;
- защищенной от ошибок в соседних модулях;
- расширяемой;
- пригодной к повторному использованию.

Типичная ошибка: считать повторное использование простым копированием кода. Копирование кода не является настоящим повторным использованием, потому что изменения приходится потом дублировать.

## 4. Абстрактные типы данных

### 4.1. Определение

Абстрактный тип данных - тип, заданный множеством операций и правилами их поведения без указания внутреннего представления.

Главная идея:

```text
пользователь знает, что можно делать с объектом, но не знает и не должен знать, как объект устроен внутри.
```

### 4.2. Пример стека

Стек задается операциями:

- `push`;
- `pop`;
- `top`;
- `empty`.

Инвариант:

```text
размер стека не может быть отрицательным.
```

Контракт `pop`:

```text
предусловие: стек не пуст;
постусловие: удален и возвращен последний добавленный элемент.
```

Реализация может быть массивом, динамическим массивом или связным списком.

### 4.3. АТД и ООП

В ООП АТД реализуется классом или интерфейсом. Инкапсуляция защищает внутреннее состояние, а методы выражают операции типа.

Ключевые концепции:

- абстракция;
- интерфейс;
- инкапсуляция;
- инвариант;
- контракт;
- независимость реализации.

### 4.4. Отличие АТД от структуры данных

АТД описывает логическое поведение. Структура данных описывает физическую организацию хранения.

```text
Стек - АТД.
Массив - структура данных.
Стек может быть реализован через массив.
```

## 5. Проектирование по контракту

### 5.1. Суть подхода

Проектирование по контракту рассматривает взаимодействие клиента и модуля как соглашение.

Клиент обязан выполнить предусловия. Модуль обязан обеспечить постусловия. Объект обязан сохранять инварианты.

### 5.2. Предусловия

Предусловие - требование перед вызовом операции.

Пример:

```text
Для sqrt(x) предусловие: x >= 0.
```

Если предусловие нарушено, виноват вызывающий код.

### 5.3. Постусловия

Постусловие - гарантия после выполнения операции.

Пример:

```text
После sort массив упорядочен и содержит те же элементы.
```

Если предусловие выполнено, но постусловие нарушено, ошибка в реализации.

### 5.4. Инварианты

Инвариант - свойство объекта, истинное после конструктора и после завершения каждого публичного метода.

Пример для банковского счета:

```text
balance >= 0
```

### 5.5. Корректность и надежность

Корректность - соответствие спецификации.

Надежность - способность сохранять корректную работу в заданных условиях.

Проектирование по контракту повышает надежность, потому что делает ожидания явными и позволяет локализовать ответственность за ошибку.

### 5.6. Выражение спецификаций

Спецификации выражаются:

- текстом;
- типами;
- интерфейсами;
- предусловиями;
- постусловиями;
- инвариантами;
- тестами;
- формальными утверждениями.

## 6. Полный устный ответ

Объектно-ориентированное программирование строит систему как совокупность взаимодействующих объектов. Ключевыми понятиями являются класс, объект, интерфейс, состояние, поведение, инкапсуляция, наследование, полиморфизм и абстракция. Модульность в ООП выражается прежде всего через классы и интерфейсы.

Качество ПО включает внешние факторы, видимые пользователю, и внутренние факторы, важные для разработки и сопровождения. Внешние факторы - корректность, надежность, удобство, эффективность, безопасность. Внутренние - модульность, читаемость, тестируемость, сопровождаемость, расширяемость.

Повторное использование достигается через функции, классы, наследование, композицию, шаблоны, библиотеки, фреймворки и паттерны. Абстрактные типы данных позволяют описывать поведение через операции без раскрытия реализации. Проектирование по контракту задает точные правила взаимодействия через предусловия, постусловия и инварианты, что повышает корректность и надежность программ.
