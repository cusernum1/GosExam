## 2. Вопрос 1. Модульное построение ПО

### 2.1. Понятие модуля

Модуль - это относительно самостоятельная часть программной системы, имеющая четко определенное назначение, интерфейс и скрытую реализацию.

Модуль может быть представлен:

- классом;
- пакетом;
- библиотекой;
- компонентом;
- подсистемой;
- отдельным сервисом;
- файлом исходного кода, если он имеет самостоятельную ответственность.

Главная идея модульности состоит в том, что сложная система разбивается на части, которые можно разрабатывать, понимать, тестировать и сопровождать относительно независимо.

### 2.2. Зачем нужно модульное построение

Модульность необходима для управления сложностью программного обеспечения.

Она позволяет:

- уменьшить объем информации, который разработчик должен держать в голове;
- локализовать изменения;
- повторно использовать готовые части;
- распределять работу между разработчиками;
- тестировать части системы независимо;
- снижать связность системы;
- повышать надежность и сопровождаемость.

Без модульности большая программа превращается в монолит, где изменение одной части может непредсказуемо повлиять на другие части.

### 2.3. Интерфейс и реализация модуля

У модуля выделяют две стороны:

- интерфейс;
- реализацию.

Интерфейс описывает, что модуль предоставляет внешнему миру.

Реализация описывает, как именно модуль выполняет свою работу.

Пример:

```cpp
class Stack {
public:
    void push(int value);
    int pop();
    bool empty() const;

private:
    int data[100];
    int top;
};
```

Открытые методы `push`, `pop`, `empty` образуют интерфейс. Массив `data` и переменная `top` являются частью реализации и скрыты от пользователя класса.

### 2.4. Подходы к повторному использованию

Повторное использование означает применение уже созданных программных элементов в новых системах или новых частях той же системы.

Основные подходы:

| Подход | Сущность | Пример |
|---|---|---|
| Повторное использование функций | Использование готовых процедур и функций | математическая библиотека |
| Повторное использование классов | Использование готовых классов | `std::vector`, `std::string` |
| Наследование | Создание нового класса на основе существующего | `Manager` наследует `Employee` |
| Композиция | Включение объекта одного класса в другой | `Car` содержит `Engine` |
| Шаблоны и обобщенное программирование | Описание алгоритмов независимо от типа | `std::vector<T>` |
| Паттерны проектирования | Повторное использование проектных решений | Singleton, Strategy, Observer |
| Компоненты и библиотеки | Использование готовых программных блоков | GUI-библиотека, ORM |
| Фреймворки | Повторное использование архитектурного каркаса | Qt, Spring, Django |

### 2.5. Наследование и композиция как способы повторного использования

Наследование выражает отношение "является".

Пример:

```text
Квадрат является прямоугольником
```

Но в программировании наследование нужно использовать осторожно. Оно создает сильную связь между базовым и производным классом.

Композиция выражает отношение "содержит".

Пример:

```text
Автомобиль содержит двигатель
```

Композиция часто предпочтительнее наследования, потому что она дает более гибкую структуру и меньше связывает классы.

Один из важных принципов объектно-ориентированного проектирования:

```text
Предпочитать композицию наследованию, если отношение наследования не является естественным.
```

### 2.6. Повторяемость

Повторяемость в контексте модульного построения означает возможность многократно применять один и тот же модуль или одно и то же проектное решение в разных местах без копирования кода и без нарушения корректности системы.

Повторяемость достигается за счет:

- ясного интерфейса;
- слабой зависимости от внешней среды;
- параметризации;
- обобщенных типов;
- отсутствия скрытых побочных эффектов;
- хорошей документации;
- тестируемости;
- соблюдения контракта модуля.

Пример плохой повторяемости:

```text
Функция работает только с глобальными переменными и зависит от конкретного файла на диске.
```

Пример хорошей повторяемости:

```text
Функция получает все данные через параметры и возвращает результат без скрытого изменения внешнего состояния.
```

### 2.7. Требования к модульным структурам

К модульным структурам предъявляются следующие требования:

| Требование | Смысл |
|---|---|
| Декомпозируемость | систему можно разбить на понятные части |
| Компонуемость | модули можно соединять в более крупные подсистемы |
| Понятность | модуль можно понять независимо от всей системы |
| Непрерывность | малое изменение требований вызывает малое изменение программы |
| Защищенность | ошибка в одном модуле не разрушает всю систему |
| Слабая связность | модуль мало зависит от других модулей |
| Высокая связность внутри | элементы модуля работают над одной задачей |
| Скрытие информации | детали реализации недоступны внешнему коду |

### 2.8. Связность и сцепление

Важнейшие характеристики модульности:

- связность внутри модуля;
- сцепление между модулями.

Хороший модуль имеет высокую внутреннюю связность и низкое внешнее сцепление.

Высокая связность означает, что все элементы модуля подчинены одной ответственности.

Низкое сцепление означает, что модуль мало зависит от деталей других модулей.

### 2.9. Экзаменационный ответ

Модульное построение программного обеспечения состоит в разбиении системы на относительно самостоятельные части, каждая из которых имеет четко определенный интерфейс и скрытую реализацию. Модульность применяется для управления сложностью, повышения надежности, облегчения сопровождения и повторного использования программных компонентов.

Повторное использование может осуществляться на разных уровнях: функций, классов, библиотек, компонентов, фреймворков и паттернов проектирования. В объектно-ориентированном программировании важными механизмами повторного использования являются наследование, композиция, полиморфизм и обобщенное программирование.

К модульным структурам предъявляются требования декомпозируемости, компонуемости, понятности, непрерывности и защищенности. Хороший модуль должен иметь высокую внутреннюю связность, слабое сцепление с другими модулями, ясный интерфейс и скрытую реализацию.

## 3. Вопрос 2. Проектирование по контракту

### 3.1. Идея проектирования по контракту

Проектирование по контракту - это подход к разработке программ, при котором взаимодействие между программными компонентами описывается через точные обязательства.

Контракт задает:

- что должен выполнить вызывающий код;
- что обязуется выполнить вызываемый модуль;
- какие свойства должны сохраняться всегда.

Идея аналогична юридическому контракту: каждая сторона имеет обязанности и гарантии.

### 3.2. Предусловия

Предусловие - это условие, которое должно быть истинно перед вызовом операции.

Предусловие является обязанностью клиента, то есть кода, который вызывает операцию.

Пример:

```cpp
int divide(int a, int b) {
    // Предусловие: b != 0
    return a / b;
}
```

Для функции деления предусловие состоит в том, что делитель не равен нулю.

Если клиент нарушил предусловие, ошибка находится на стороне клиента.

### 3.3. Постусловия

Постусловие - это условие, которое должно быть истинно после завершения операции.

Постусловие является обязанностью поставщика, то есть вызываемого модуля.

Пример:

```text
После вызова push(x) размер стека увеличивается на 1, а верхний элемент равен x.
```

Если предусловие было выполнено, но постусловие нарушено, ошибка находится в реализации операции.

### 3.4. Инварианты

Инвариант - это условие, которое должно сохраняться для объекта во всех устойчивых состояниях.

Пример инварианта стека:

```text
0 <= size <= capacity
```

Пример инварианта банковского счета:

```text
balance >= 0
```

Инвариант должен быть истинным после создания объекта и после завершения каждого открытого метода.

### 3.5. Корректность ПО

Корректность программного обеспечения означает соответствие программы ее спецификации.

Если программа делает именно то, что указано в спецификации, она является корректной.

Различают:

- частичную корректность;
- полную корректность.

Частичная корректность означает: если программа завершилась, то результат правильный.

Полная корректность означает: программа завершится и результат будет правильным.

### 3.6. Надежность ПО

Надежность программного обеспечения - это способность программы сохранять работоспособность и корректно выполнять функции при заданных условиях эксплуатации.

Надежность связана с:

- корректностью;
- обработкой ошибок;
- устойчивостью к неверным данным;
- тестированием;
- простотой архитектуры;
- отсутствием скрытых зависимостей;
- контролем инвариантов.

### 3.7. Выражение спецификаций

Спецификация может выражаться:

- естественным языком;
- математическими условиями;
- типами данных;
- предусловиями;
- постусловиями;
- инвариантами;
- тестами;
- интерфейсами;
- диаграммами UML;
- формальными языками спецификаций.

Пример спецификации операции `pop` для стека:

```text
Предусловие:
стек не пуст.

Постусловие:
возвращен элемент, который был добавлен последним;
размер стека уменьшился на 1.

Инвариант:
размер стека остается в пределах от 0 до capacity.
```

### 3.8. Проектирование по контракту и исключения

Важно отличать нарушение контракта от исключительной ситуации.

Если клиент вызывает метод с недопустимыми параметрами, это нарушение предусловия.

Если произошла внешняя проблема, например не удалось открыть файл, это исключительная ситуация.

Нарушения контракта обычно указывают на ошибку в программе. Исключительные ситуации могут возникать во время нормальной работы и должны обрабатываться.

### 3.9. Экзаменационный ответ

Проектирование по контракту - это метод построения надежного программного обеспечения, при котором поведение модулей задается через предусловия, постусловия и инварианты. Предусловия описывают обязанности клиента перед вызовом операции. Постусловия описывают гарантии операции после выполнения. Инварианты задают свойства объекта, сохраняющиеся во всех устойчивых состояниях.

Корректность ПО означает соответствие программы спецификации. Надежность ПО связана со способностью программы правильно работать в заданных условиях и сохранять устойчивость при ошибках. Спецификации могут выражаться естественным языком, формальными условиями, интерфейсами, типами, тестами и инвариантами.

## 4. Вопрос 3. ООП. Модульность. Критерии, правила, принципы

### 4.1. Понятие ООП

Объектно-ориентированное программирование - это парадигма программирования, в которой программа строится как совокупность взаимодействующих объектов.

Объект объединяет:

- состояние;
- поведение;
- идентичность.

Состояние представлено полями объекта.

Поведение представлено методами.

Идентичность означает, что каждый объект является самостоятельной сущностью, даже если его состояние совпадает с состоянием другого объекта.

### 4.2. Класс и объект

Класс - это описание множества объектов с одинаковой структурой и поведением.

Объект - это экземпляр класса.

Пример:

```cpp
class Point {
public:
    int x;
    int y;
};

Point p;
```

`Point` - класс, а `p` - объект.

### 4.3. Основные принципы ООП

К основным принципам ООП относятся:

- абстракция;
- инкапсуляция;
- наследование;
- полиморфизм.

### 4.4. Абстракция

Абстракция означает выделение существенных свойств объекта и отвлечение от несущественных деталей.

Например, для класса `BankAccount` важны:

- баланс;
- пополнение;
- снятие;
- проверка состояния.

Но не важны внутренние детали хранения данных.

### 4.5. Инкапсуляция

Инкапсуляция означает объединение данных и методов в одном объекте, а также скрытие внутренней реализации.

Пример:

```cpp
class BankAccount {
public:
    void deposit(double amount);
    bool withdraw(double amount);
    double getBalance() const;

private:
    double balance;
};
```

Поле `balance` скрыто. Внешний код работает через методы.

### 4.6. Наследование

Наследование позволяет строить новый класс на основе существующего.

Базовый класс содержит общие свойства и методы.

Производный класс расширяет или уточняет поведение базового класса.

Пример:

```cpp
class Shape {
public:
    virtual double area() const = 0;
};

class Circle : public Shape {
public:
    double area() const override;
};
```

### 4.7. Полиморфизм

Полиморфизм означает возможность работать с объектами разных типов через общий интерфейс.

Пример:

```cpp
void printArea(const Shape& shape) {
    cout << shape.area();
}
```

Функция может принимать любой объект, являющийся фигурой.

### 4.8. Модульность в ООП

В ООП класс является естественной единицей модульности.

Хороший класс должен:

- иметь одну ответственность;
- скрывать внутреннее состояние;
- предоставлять ясный интерфейс;
- быть слабо связанным с другими классами;
- быть тестируемым;
- поддерживать повторное использование.

### 4.9. Критерии модульности

Критерии хорошей модульности:

| Критерий | Смысл |
|---|---|
| Декомпозируемость | задачу можно разбить на части |
| Компонуемость | модули можно собирать в новые системы |
| Понятность | модуль можно понять отдельно |
| Непрерывность | небольшое изменение требований вызывает небольшое изменение кода |
| Защищенность | ошибка локализуется внутри модуля |

### 4.10. Правила модульности

Основные правила:

1. Прямое отображение.
2. Малое число интерфейсов.
3. Малые интерфейсы.
4. Явные интерфейсы.
5. Скрытие информации.

Прямое отображение означает, что структура программы должна соответствовать структуре предметной области.

Малое число интерфейсов означает, что модуль не должен иметь слишком много точек связи с другими модулями.

Малые интерфейсы означают, что модуль должен открывать только необходимые операции.

Явные интерфейсы означают, что зависимости должны быть видны в коде.

Скрытие информации означает, что внутренние детали модуля не должны быть доступны извне.

### 4.11. Принципы модульности

В ООП важны следующие принципы:

- единственная ответственность;
- открытость/закрытость;
- подстановка Лисков;
- разделение интерфейсов;
- инверсия зависимостей.

Эти принципы часто объединяют в набор SOLID.

### 4.12. SOLID

Принцип единственной ответственности:

```text
Класс должен иметь только одну причину для изменения.
```

Принцип открытости/закрытости:

```text
Программные сущности должны быть открыты для расширения, но закрыты для изменения.
```

Принцип подстановки Лисков:

```text
Объекты производного класса должны быть заменяемы объектами базового класса без нарушения корректности программы.
```

Принцип разделения интерфейсов:

```text
Лучше иметь несколько специализированных интерфейсов, чем один общий и перегруженный.
```

Принцип инверсии зависимостей:

```text
Код должен зависеть от абстракций, а не от конкретных реализаций.
```

### 4.13. Экзаменационный ответ

ООП представляет программу как совокупность взаимодействующих объектов. Основными понятиями являются класс, объект, состояние, поведение и идентичность. Основные принципы ООП - абстракция, инкапсуляция, наследование и полиморфизм.

Модульность в ООП выражается прежде всего через классы и интерфейсы. Хороший объектно-ориентированный модуль должен иметь ясную ответственность, скрытую реализацию, небольшой интерфейс, слабую зависимость от других модулей и высокую внутреннюю связность. Критериями модульности являются декомпозируемость, компонуемость, понятность, непрерывность и защищенность.

## 5. Вопрос 4. Абстрактные типы данных в ООП

### 5.1. Понятие абстрактного типа данных

Абстрактный тип данных - это математическая модель данных, определяемая множеством значений и набором операций над ними, без указания внутренней реализации.

Иными словами, абстрактный тип данных описывает не то, как данные хранятся, а то, какие операции с ними можно выполнять.

Примеры абстрактных типов данных:

- стек;
- очередь;
- список;
- множество;
- словарь;
- дерево;
- граф.

### 5.2. Пример: стек

Стек - это абстрактный тип данных, работающий по принципу LIFO.

LIFO означает:

```text
last in, first out
```

То есть последним добавленный элемент извлекается первым.

Операции стека:

- `push` - добавить элемент;
- `pop` - удалить и вернуть верхний элемент;
- `top` - посмотреть верхний элемент;
- `empty` - проверить, пуст ли стек.

При этом реализация может быть разной:

- массив;
- связный список;
- динамический контейнер.

### 5.3. Абстрактный тип данных и класс

В ООП абстрактный тип данных обычно реализуется через класс.

Класс задает:

- закрытое представление данных;
- открытые операции;
- инварианты;
- правила использования.

Пример:

```cpp
class Stack {
public:
    void push(int value);
    int pop();
    bool empty() const;

private:
    vector<int> data;
};
```

Пользователь класса не знает, как именно хранится стек. Он работает только через операции.

### 5.4. Ключевые концепции АТД в ООП

Ключевые концепции:

| Концепция | Смысл |
|---|---|
| Абстракция | описание сущности через операции |
| Инкапсуляция | скрытие внутреннего представления |
| Интерфейс | набор доступных операций |
| Инвариант | условие корректности состояния |
| Контракт | правила вызова операций |
| Независимость реализации | возможность менять внутреннее устройство без изменения интерфейса |

### 5.5. Преимущества АТД

Абстрактные типы данных дают:

- упрощение понимания программы;
- защиту от некорректного доступа к данным;
- возможность менять реализацию;
- повторное использование;
- повышение надежности;
- более ясное проектирование.

### 5.6. Отличие АТД от структуры данных

Абстрактный тип данных описывает логическое поведение.

Структура данных описывает конкретную организацию хранения.

Например:

```text
Стек - абстрактный тип данных.
Массив или связный список - структуры данных, через которые стек может быть реализован.
```

### 5.7. Экзаменационный ответ

Абстрактный тип данных - это тип, определяемый множеством допустимых значений и операций над ними без раскрытия внутренней реализации. В ООП абстрактные типы данных реализуются с помощью классов и интерфейсов. Класс скрывает представление данных и предоставляет операции, через которые пользователь взаимодействует с объектом.

Ключевыми концепциями АТД являются абстракция, инкапсуляция, интерфейс, инвариант и независимость реализации. Примерами АТД являются стек, очередь, список, множество и словарь.

## 6. Вопрос 5. Качество ПО

### 6.1. Понятие качества ПО

Качество программного обеспечения - это совокупность свойств программы, определяющих ее способность удовлетворять заданные и предполагаемые потребности пользователей.

Качество ПО оценивается не только по тому, работает ли программа сейчас, но и по тому, насколько ее удобно сопровождать, изменять, тестировать и использовать.

### 6.2. Внешние факторы качества

Внешние факторы качества видны пользователю или заказчику.

К ним относятся:

| Фактор | Смысл |
|---|---|
| Корректность | программа соответствует спецификации |
| Надежность | программа стабильно работает в заданных условиях |
| Удобство использования | пользователю легко работать с системой |
| Эффективность | программа рационально использует ресурсы |
| Безопасность | данные и функции защищены |
| Совместимость | программа работает с нужными платформами и системами |
| Функциональность | программа реализует требуемые функции |

### 6.3. Внутренние факторы качества

Внутренние факторы качества видны главным образом разработчикам.

К ним относятся:

| Фактор | Смысл |
|---|---|
| Читаемость | код легко понимать |
| Модульность | код разделен на понятные части |
| Сопровождаемость | код легко исправлять и развивать |
| Тестируемость | код удобно проверять тестами |
| Расширяемость | можно добавлять новые возможности |
| Повторное использование | компоненты можно применять повторно |
| Низкая связность | модули мало зависят друг от друга |
| Высокая связность внутри | модуль имеет ясную ответственность |

### 6.4. Связь внешних и внутренних факторов

Внешнее качество зависит от внутреннего.

Например:

- надежность зависит от простоты и тестируемости кода;
- расширяемость зависит от модульности;
- корректность зависит от ясности спецификаций;
- безопасность зависит от архитектуры и контроля доступа;
- эффективность зависит от алгоритмов и структур данных.

Пользователь может не видеть внутреннее качество, но его отсутствие со временем приводит к ошибкам, дорогому сопровождению и невозможности развивать систему.

### 6.5. Качество и ООП

ООП помогает повышать качество ПО за счет:

- инкапсуляции;
- абстракции;
- полиморфизма;
- повторного использования;
- паттернов проектирования;
- разделения ответственности;
- слабого сцепления модулей.

Но ООП само по себе не гарантирует качество. Плохая объектная модель может ухудшить систему, если классы имеют неясную ответственность, слишком сильные связи или нарушают инкапсуляцию.

### 6.6. Паттерны проектирования и качество

Паттерны проектирования - это типовые решения часто встречающихся задач проектирования.

Они повышают качество, потому что:

- дают проверенные архитектурные решения;
- улучшают повторяемость проектирования;
- делают систему понятнее для разработчиков;
- уменьшают зависимость от конкретных реализаций;
- помогают расширять систему без переписывания существующего кода.

Примеры паттернов:

| Паттерн | Назначение |
|---|---|
| Strategy | замена алгоритмов без изменения клиента |
| Observer | уведомление зависимых объектов об изменениях |
| Factory Method | создание объектов через общий интерфейс |
| Adapter | согласование несовместимых интерфейсов |
| Decorator | динамическое добавление поведения |

### 6.7. Экзаменационный ответ

Качество программного обеспечения - это совокупность характеристик, определяющих способность программы удовлетворять требованиям пользователя и заказчика. Различают внешние и внутренние факторы качества.

Внешние факторы видны пользователю: корректность, надежность, эффективность, удобство использования, безопасность, совместимость. Внутренние факторы видны разработчику: модульность, читаемость, сопровождаемость, тестируемость, расширяемость, повторное использование, слабое сцепление и высокая связность модулей.

Внутреннее качество является основой внешнего качества. ООП способствует повышению качества за счет абстракции, инкапсуляции, полиморфизма, повторного использования и применения паттернов проектирования.

## 8. Короткая версия для повторения

Модуль - самостоятельная часть программы с интерфейсом и скрытой реализацией.

Хороший модуль имеет:

```text
высокую внутреннюю связность и низкое внешнее сцепление
```

Проектирование по контракту задает:

```text
предусловия, постусловия, инварианты
```

Основные принципы ООП:

```text
абстракция, инкапсуляция, наследование, полиморфизм
```

Абстрактный тип данных описывает:

```text
операции и поведение, но не внутреннюю реализацию
```

Качество ПО делится на:

```text
внешнее качество для пользователя и внутреннее качество для разработчика
```
