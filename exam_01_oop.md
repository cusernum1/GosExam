Файл подготовлен как отдельный экзаменационный конспект по блоку ООП. Основа: ранее указанные источники по ООП, паттернам проектирования, C/C++ и общие учебные определения объектно-ориентированного проектирования.

## 1. Качество ПО. Внешние и внутренние факторы

Качество программного обеспечения - это совокупность свойств программы, определяющих ее способность удовлетворять заданные и предполагаемые потребности пользователей, заказчиков и разработчиков.

Качество удобно делить на внешнее и внутреннее.

Внешние факторы качества видны пользователю:

| Фактор | Смысл |
|---|---|
| Корректность | программа соответствует спецификации |
| Надежность | программа устойчиво работает при заданных условиях |
| Удобство использования | пользователю удобно выполнять задачи |
| Эффективность | программа рационально использует время и память |
| Безопасность | система защищает данные и операции |
| Совместимость | программа взаимодействует с нужными платформами и системами |
| Функциональная полнота | реализованы необходимые функции |

Внутренние факторы качества видны прежде всего разработчику:

| Фактор | Смысл |
|---|---|
| Читаемость | код легко понимать |
| Модульность | система разделена на понятные части |
| Сопровождаемость | код легко исправлять и развивать |
| Тестируемость | поведение удобно проверять тестами |
| Расширяемость | можно добавлять новые возможности |
| Повторное использование | компоненты можно применять в других местах |
| Низкая связность | модули мало зависят друг от друга |
| Высокая связность внутри | элементы модуля решают одну задачу |

Внешнее качество часто зависит от внутреннего. Например, надежность трудно обеспечить, если код плохо структурирован и не тестируется. Расширяемость невозможна без модульности. Корректность невозможна без ясных спецификаций.

Экзаменационная формулировка:

```text
Качество ПО определяется как соответствие программы требованиям и ожиданиям пользователей, а также пригодность программы к сопровождению и развитию. Внешние факторы отражают свойства, наблюдаемые пользователем, а внутренние характеризуют устройство программы и важны для разработчиков.
```

## 2. Модульность. Критерии, правила, принципы

Модульность - это свойство программной системы быть разбитой на относительно независимые части, каждая из которых имеет четкую ответственность, интерфейс и скрытую реализацию.

Модуль может быть классом, пакетом, библиотекой, компонентом, сервисом или подсистемой.

Критерии модульности:

| Критерий | Содержание |
|---|---|
| Декомпозируемость | систему можно разбить на более простые части |
| Компонуемость | модули можно объединять в новые системы |
| Понятность | модуль можно понять отдельно от всей системы |
| Непрерывность | малое изменение требований вызывает малое изменение кода |
| Защищенность | ошибка в одном модуле не разрушает всю систему |

Правила модульности:

1. Прямое отображение структуры предметной области в структуру программы.
2. Малое число интерфейсов между модулями.
3. Небольшой размер интерфейсов.
4. Явность зависимостей.
5. Скрытие информации.

Основные принципы:

- высокая внутренняя связность;
- слабое сцепление между модулями;
- единственная ответственность;
- минимальный публичный интерфейс;
- зависимость от абстракций, а не от деталей реализации;
- локализация изменений.

В ООП класс является естественной единицей модульности. Хороший класс имеет одну ответственность, скрывает данные, предоставляет понятный интерфейс и не зависит от лишних деталей других классов.

## 3. Подходы к повторному использованию. Повторяемость

Повторное использование - это применение ранее созданных программных элементов или проектных решений в новых задачах.

Подходы:

| Подход | Пример |
|---|---|
| Использование функций | математические функции, утилиты |
| Использование классов | контейнеры, строки, классы доменной модели |
| Наследование | расширение поведения базового класса |
| Композиция | объект содержит другие объекты |
| Шаблоны | обобщенные контейнеры и алгоритмы |
| Библиотеки | готовые программные компоненты |
| Фреймворки | готовый архитектурный каркас |
| Паттерны проектирования | повторное использование схем решения |

Наследование выражает отношение "является". Композиция выражает отношение "содержит". В проектировании часто предпочитают композицию наследованию, если наследование не отражает естественную и устойчивую иерархию.

Повторяемость - это возможность многократно применять модуль или решение без копирования кода и без нарушения корректности.

Для повторяемости нужны:

- ясный интерфейс;
- независимость от глобального состояния;
- параметризация;
- слабые зависимости;
- документированный контракт;
- тестируемость;
- устойчивые инварианты.

Требования к модульным структурам:

```text
модули должны быть понятными, независимыми, защищенными от внешнего вмешательства, пригодными к композиции и повторному использованию.
```

## 4. Абстрактные типы данных. Ключевые концепции

Абстрактный тип данных - это тип, определяемый набором значений и операций над ними без указания внутренней реализации.

Примеры АТД:

- стек;
- очередь;
- список;
- множество;
- словарь;
- дерево;
- граф.

Пример: стек определяется операциями `push`, `pop`, `top`, `empty`, но не тем, хранится он в массиве или связном списке.

Ключевые концепции:

| Концепция | Смысл |
|---|---|
| Абстракция | выделение существенного поведения |
| Инкапсуляция | скрытие представления данных |
| Интерфейс | набор доступных операций |
| Инвариант | условие корректного состояния |
| Контракт | правила вызова операций |
| Независимость реализации | реализацию можно менять без изменения клиента |

В ООП абстрактный тип данных обычно реализуется через класс или интерфейс.

Пример:

```cpp
class Stack {
public:
    void push(int value);
    int pop();
    bool empty() const;
private:
    std::vector<int> data;
};
```

Пользователь класса знает операции, но не обязан знать внутреннее хранение.

## 5. Проектирование по контракту. Надежность и корректность ПО

Проектирование по контракту - это подход, при котором поведение программных компонентов задается через обязательства и гарантии.

Основные элементы:

- предусловия;
- постусловия;
- инварианты.

Предусловие - условие, которое должно быть истинно до вызова операции. Это обязанность клиента.

Пример:

```text
Для операции деления предусловие: делитель не равен нулю.
```

Постусловие - условие, которое должно быть истинно после выполнения операции. Это обязанность поставщика.

Пример:

```text
После push(x) верхний элемент стека равен x, а размер стека увеличился на 1.
```

Инвариант - условие, сохраняющееся для объекта во всех устойчивых состояниях.

Пример:

```text
0 <= size <= capacity
```

Корректность ПО означает соответствие программы спецификации.

Частичная корректность:

```text
если программа завершилась, то результат правильный.
```

Полная корректность:

```text
программа завершится и результат будет правильным.
```

Надежность ПО - способность программы сохранять работоспособность и корректно выполнять функции при заданных условиях.

Спецификации могут выражаться:

- естественным языком;
- типами данных;
- интерфейсами;
- предусловиями;
- постусловиями;
- инвариантами;
- тестами;
- формальными моделями.

Экзаменационная формулировка:

```text
Проектирование по контракту повышает надежность ПО, потому что явно фиксирует обязанности клиента и поставщика. Предусловия описывают допустимость вызова, постусловия - гарантированный результат, инварианты - устойчивые свойства объекта.
```
